# Full update с сохранением MCP и основной идеи

Используй только после явного выбора Full update. Выбор включает согласие на предупреждённые затраты deep scan в указанном scope, но не расширяет права на внешние системы, публикацию, изменение клиентского кода или credentials.

## Что обновляется и что остаётся

- Пересобираются все подтверждённые наши активные skills, их инженерные references, RAG/knowledge index, карты, исследование/evidence, inputs/assembly и производные validation/state. Устаревшие skills выводятся из registry после проверки новой замены, не остаются скрыто активными.
- Старая рабочая история, планы задач, research notes/logs и устаревшие выводы не переходят в новый контекст. Не подмешивай их в fresh evidence и не загружай старую RAG автоматически.
- Сохраняется основная идея: назначение продукта, для кого он, важные бизнес-ограничения и явно принятые решения, которые по-прежнему действуют. Сожми это в `.agent-state/project-intent.md` выбранного storage. Не сохраняй весь worklog под видом «основной идеи». Существующий intent сохрани и уточни только по подтверждённым данным; спорные решения не превращай в неизменный закон.
- Сохраняются MCP-серверы и их имена/команды/transport, env/credentials sources, доступы и зарегистрированные подключения; локальные runtime/helpers, `.local`, `.tmp`, env files, Git remotes/credentials, CI policy, `workspace.json`/`agent-storage.json`, `.gitignore` и клиентские правила. Внешний пользовательский MCP config не перемещай и не переписывай.
- Название файла — только сигнал: если настройки MCP спрятаны в старом skill или RAG, до замены выдели их в защищённую конфигурацию без вывода секретов. Не удаляй рабочий helper вместе с содержимым skill. Не трогай реальные БД приложения; «базы» здесь означает нашу агентскую RAG/knowledge, не product database.

## Порядок

1. Проверь выбранные scope/storage, возможность реальной безопасной новой сборки и разделение по `repository-separation.md`. Если compiler workflow недоступен для выбранного storage, остановись до deep scan и сноса, сохранив текущую систему. Если есть перенос, сначала сохрани материалы в выбранном Git/local месте. Full не выбирает storage заново и не отменяет запрет публикации для local.
2. Сними план `update --mode full --check` и уточни ownership для всех кандидатов. Не удаляй каталоги целиком по названиям. Раздели подтверждённые наши знания/skills, устаревшую рабочую историю, настройки и неизвестное. Любой неизвестный путь сохраняется до решения.
3. Сохрани короткий project intent. Зафиксируй protected paths и контрольные суммы конфигурации, не содержимое credentials. Уточни точные источники MCP settings из уже известной конфигурации, не ищи токены/серверы по всему home. Выполни доступный read-only baseline probe по существующему transport; отсутствие доступа фиксируется как gap, а не повод перенастроить MCP.
4. Создай отдельный проверенный checkpoint старого поколения в `.agent-history/<run-id>/` внутри выбранного storage. Копируй только подтверждённые заменяемые артефакты и короткий manifest; не копируй `.git`, env/secret config или содержимое внешних settings. При секретах, случайно найденных в RAG, не публикуй такой backup — сначала безопасно разреши утечку. Manifest содержит режим, версии, scope, пути/digests, статус и указание `not-active-knowledge`, без credentials.
5. Подготовь новое поколение в отдельной рабочей области storage, пока старое остаётся активным. Не сбрасывай live bootstrap-state и не запускай install wizard/enterprise configure. Для deep scan прочитай актуальные research-инструкции toolkit и исследуй исходники заново: архитектура, реальные flows, контракты, риски, тесты/CI, security/performance. Старое исследование — только историческая подсказка, не доказательство; каждый новый вывод подтверждай свежими источниками.
6. Собери новую RAG и весь применимый набор skills под новые стандарты, сохранив core intent и клиентские правила. Используй реальный поддерживаемый assembly/compiler workflow с выполненными prerequisites. Не подделывай state/evidence и не объявляй ручной текст результатом renderer. Если текущий compiler не поддерживает безопасную отдельную сборку (в частности, полный non-Git pipeline пока не поддержан), остановись ДО удаления/переключения и сообщи ограничение. Full plan сам по себе не означает готовый rebuild engine.
7. До активации проверь полную coverage, ссылки, registry/router, отсутствие старых активных skills/истории, сохранность client rules/intent и неизменность protected settings. Повтори доступные MCP probes теми же именами и transport; ничего не переустанавливай. Если baseline уже был недоступен, не заявляй «всё работает» без проверки; отличие конфигурации или новая регрессия блокируют активацию.
8. После успешных проверок замени только allowlisted активные артефакты новой сборкой; старое поколение удаляется из active roots/index/router. История разработки/Git не переписывается. Не вызывай `rm -rf docs/agent-system` или удаление всей папки skills: там могут быть защищённые настройки и не наши файлы. Перед каждым изменением проверь, что исходные digests не изменились другой работой. Существующие renderer ownership gates не обходи без явного решения о конкретных файлах.
9. Проверь активное поколение повторно. При сбое восстанови только собственные изменения из checkpoint, если нет новых пользовательских правок. Старый checkpoint не добавляй в knowledge-index/skill-registry; история обновления остаётся короткой, без старого рабочего контекста. Удаление backup — отдельное решение о сроке хранения, не часть слепого cleanup.

## Настройки, история и публикация

Full не обнуляет серверы MCP, доступы, env, runtime или выбранный Git/local режим. Крупное обновление runtime/MCP — отдельная задача, не скрытая часть пересборки skills. Не регистрируй серверы повторно ради нового RAG.

Основная идея остаётся активной; остальная старая история не читается в обычной работе. Технический checkpoint служит только откату и не считается текущими знаниями. Git commits/MR истории не переписываются и не удаляются.

Для Git storage публикация — только по запросу, с отдельными MR по `git-remote-flow`. Для local — без agent staging/commit/push/MR; текущий перенос и cleanup ничего не коммитят в customer Git. Ответ различает выбор режима, готовность новой сборки, активацию, MCP checks, сохранённый intent, исключённую старую историю и публикацию. Не называй Full завершённым, если создан только план или новая сборка не активирована.
