# Выборочное обновление установленной системы

Используй только для выбранного incremental/бережного режима после `update-modes.md`. Обновление сохраняет работающие наработки, skills, RAG и историю; исправляет критичные ошибки, несовместимые форматы/версии и существенные применимые требования. Никакого сноса, массовой перегенерации, full research или удаления истории. MCP-серверы, их runtime/config и доступы сохраняются. Исправление ошибок MCP-конфигурации или обновление библиотек продукта — отдельная согласованная задача, не скрытая часть update.

## Порядок

1. До чтения всей RAG проверь разделение по `repository-separation.md`. Если отдельное назначение ещё не выбрано, спроси: Git-репозиторий или локальная папка без Git. Для local прочитай `local-agent-storage.md`; отсутствие remote в этом режиме не blocker. До выбора/проверки назначения не пиши update artifacts.
2. Установи целевую локальную версию toolkit по package version и фактическому содержимому. Не загружай случайный latest/ветку, не заменяй модифицированную копию toolkit и не угадывай версию legacy установки по одному имени файла.
3. Составь inventory всей установленной системы: RAG/index, skills с references/scripts, rules, registry, inputs, evidence и локальные доработки. Используй только явно заданные roots. Отсутствие новых служебных JSON не означает плохой skill.
4. Сначала выполни дешёвые проверки хешей, структуры, ссылок и применимых требований. На первой неизвестной установке прочитай все проектные skills для смысловой оценки, но не весь source. При повторном запуске переиспользуй только проверку, связанную с теми же содержимым, источниками и требованиями. Сам по себе совпавший хеш не доказывает качество.
5. Проверь RAG против связанных исходников; включи новые/удалённые файлы, manifests, общие конфигурации и межмодульные зависимости. Не обновляй fingerprint без проверки оснований. Если зависимости неизвестны, расширь scope и отрази неопределённость; full research требует согласования затрат.
6. Раздели результат по каждому артефакту: оставить, косметика (пропустить), существенное исправление, дополнительное evidence, конфликт. Существенны безопасность/границы записи, достоверность commands/references, актуальность RAG, authority/routing и проверяемость результата; не переписывай всё ради новой формы текста.
7. Составь минимальный план, сохрани базу и локальные правки. При наличии прежней версии используй трёхстороннее сравнение; без неё — адресные предложения, не слепое присвоение ownership. Существующие skills могут остаться в legacy-формате, если совместимы: не выдумывай для них inputs/assembly или историю проверки.
8. Подготовь правки отдельно, проверь links, authority, router, commands и отсутствие потери проектных правил. Применяй только согласованные изменения, после повторной проверки исходных digests. Используй существующие renderer/validators только если реально выполнены их prerequisites; не подделывай bootstrap state для обхода gate.
9. Закрой отчёт: что сохранено/изменено, что осталось неизвестным, какие проверки реально выполнены, Git separation и отдельный статус публикации. Блокеры/непроверенные области не считаются обновлёнными.

## Текущая граница автоматизации

`bootstrap.js update <root> --mode incremental --check` реализует read-only preflight режима/разделения. Без --mode требуется выбор пользователя. Нулевой exit code не означает соответствие всей RAG новым стандартам: команда не переносит/удаляет файлы, не выставляет installed version и не делает semantic review. Перенос и адресное обновление выполняет агент по выбранной инструкции. `--apply`, автоматическая цепочка миграций и кэш смысловых проверок ещё не реализованы; не вызывай и не имитируй их.

Preflight понимает Git sidecar через `workspace.json` и non-Git local storage через `agent-storage.json`. Для local проверяются отсутствие Git, `.gitignore`, publication=never и явно заданные корни исходников; remote не требуется. Local runtime разрешает только read-only status/doctor/commit-plan/update и запрещает Git-backed install/sync/integrations setup. Full bootstrap compiler в local storage пока не поддержан — не создавай Git для обхода этого ограничения.

Текущие research/renderer gates используют общий project fingerprint. Не запускай массовые discovery/research/repair команды только ради этой инвентаризации: они могут пометить всё исследование и inputs устаревшими. Для выборочного анализа используй read-only проверки и честно отделяй их от full bootstrap validation.
