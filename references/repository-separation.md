# Разделение продуктового кода и агентского хранения

## Обязательная проверка при обновлении

Продуктовый код принадлежит customer repository. Наши RAG, skills, research, generated rules, skill inputs/assembly, registry и agent runtime хранятся отдельно: в artifact Git-репозитории ИЛИ в локальной пользовательской папке без Git. Выбор делает пользователь. Исходники toolkit остаются отдельным источником инструмента. Project-local установка — поддерживаемый вход для миграции, но не конечное состояние обновления по этому правилу. Ниже «artifact root» означает выбранное отдельное хранилище, не обязательно Git.

Проверь разделение до дорогого research и любых записей обновления. Используй локальный `bootstrap.js update <root> --check`: это read-only инвентаризация, не автоматический перенос и не оценка качества RAG. Проверяй только текущий проект и явно перечисленные в workspace manifest репозитории; не ищи установки в home, plugins, node_modules или соседних проектах без явного пути.

Классифицируй найденное как наши артефакты, клиентские правила, смешанные файлы или неизвестное происхождение. Имя `AGENTS.md`, `.codex` или `SKILL.md` само по себе не доказывает наше владение. Учитывай managed markers, ownership manifest, registry, ссылки и историю Git. Каталоги `codex-skills`, `docs/agent-system` и toolkit — сигналы для проверки, а не разрешение удалить всё внутри. Проверяй tracked, staged, untracked и известные ignored agent paths. Не читай env/credentials ради классификации.

Если наших артефактов в клиентском репозитории нет, проверь уже выбранное хранилище: artifact remote для Git или `agent-storage.json`/папку для local. Не спрашивай выбор заново без причины и не требуй remote у local storage. Если нет ни установленной агентской системы, ни её manifest, сообщи «установка не найдена»; не создавай новую через update.

## Выбор места хранения

Если обнаружены наши агентские файлы в customer repository, а место хранения ещё не выбрано, покажи короткую сводку категорий и спроси:

«Куда перенести наши skills/RAG: в отдельный Git-репозиторий или локально у тебя, без коммитов и push?»

После выбора Git запроси URL либо checkout с remote. После выбора local используй указанный путь или предложи отдельную постоянную пользовательскую папку; затем прочитай `local-agent-storage.md`. Локальный checkout Git и локальная папка без Git — разные варианты. Не выбирай Git автоматически и не считай local временным degraded-режимом.

До выбора и определения безопасного назначения не переноси, не удаляй, не ставь файлы в index и не запускай повторный bootstrap. Read-only анализ можно закончить. Отказ от обоих вариантов переноса означает явный separation blocker, а не успешное обновление. Не создавай новый remote repository вместо запроса адреса.

Для Git после получения адреса проверь, что назначение действительно предназначено для этих проектных материалов и его доступность/аудитория допустимы. RAG может раскрывать архитектуру, код и внутренние ссылки заказчика: неизвестная видимость или право хранения требует уточнения, а не предположения, что любой Git безопасен. Не отправляй материалы в публичный репозиторий без отдельного явного разрешения на такое раскрытие. Для local проверь выбранный путь, границы и доступ; не настраивай Git/remote.

## План переноса

1. Проверь customer root, origin, ветку, worktree и index. Для Git-назначения также проверь его root, fetch/push URLs, ветку и index: оно не может быть тем же remote/checkout, вложенным customer Git или произвольно выбранным соседним проектом. Для local проверь папку вне всех Git roots, `.gitignore` и publication=never по `local-agent-storage.md`. При недоступности остановись без fallback назначения и без потери источника. Чтение remote не доказывает право push.
2. Запиши в выбранном artifact root план: storage mode, source repository/path, destination path, тип владения, исходный digest, planned action и причина. Отдельно зафиксируй HEAD/index/dirty изменения и исходные копии затрагиваемых файлов. Не забирай unrelated changes пользователя.
3. Переноси подтверждённые агентские материалы вместе с нужными supporting references/scripts, custom skills, research/evidence, inputs/assembly и конфигурацией маршрутизации без секретов. Не копируй source code целиком, `.git`, env, токены, логи с секретами или чужие product docs. Не регенерируй хорошие skills ради переноса. Не следуй symlinks за пределы явно разрешённых roots; внешняя цель требует отдельного решения. Если index и worktree различаются, сохрани обе версии и не выбирай одну молча.
4. Смешанный `AGENTS.md` разделяй по подтверждённой границе: наш managed-блок — в artifact rules, клиентские правила остаются байт-в-байт. Для неразмеченного смешанного текста сначала получи решение о разделении. Не удаляй файл целиком по имени.
5. Если destination уже содержит материалы, сначала сравни их и разреши коллизии имён, authority и registry. Сохрани обе версии до решения; не применяй last-write-wins. Не дублируй активный skill с тем же именем.
6. Сначала копируй в staging area/backup внутри artifact root. Проверь полноту и digest копий, затем отдельно проверь необходимые преобразования ссылок. Переход на `repo://<id>/<path>` и обновление registry/authority не должны превращать устаревшие evidence в свежие. Проверь source links, skill references, router и сохранность локальных правил.
7. Только после проверки назначения удаляй подтверждённые исходные agent-only файлы либо наш managed-блок. Уже tracked артефакты требуют cleanup diff в customer Git; `.gitignore` не удаляет их из истории. Не переписывай историю Git. Для ignored/untracked артефактов Git-backup недостаточен — нужна проверенная файловая копия.
8. Для Git создай/проверь `workspace.json` с явными paths/remotes; для local — `agent-storage.json` и `.gitignore` без Git-only manifest. Настрой внешний entrypoint/skills links за пределами customer repositories. Клиентские правила остаются authoritative для продуктового Git. Если среда не обнаруживает внешние skills, сообщи ограничение и дай явный локальный путь запуска, не копируй skills обратно в customer Git.

## Узкое исключение для cleanup

Обычные sidecar bootstrap/update не меняют customer worktree. Единственное исключение здесь — согласованный перенос обнаруженных агентских артефактов после получения назначения: разрешены только перечисленные в migration plan удаления agent-only файлов и извлечение нашего блока из смешанного файла. Продуктовый код и клиентские правила менять нельзя.

До и после cleanup сравни файлы, HEAD и index с исходным snapshot. Все отличия обязаны укладываться в allowlist конкретного плана; unrelated и concurrent edits не принимаются автоматически. В local mode index/HEAD остаются неизменными: никаких staging/commit/push во время переноса, cleanup остаётся рабочим diff. В Git sidecar старый `workspace-verify` закономерно увидит cleanup как изменение: не обходи это молчаливым пересозданием snapshot. Сначала проверь cleanup diff по плану, сохрани результат, и только затем создай post-migration baseline для дальнейшего обычного update. Pending cleanup коммиты не равны полностью завершённой публикации.

При сбое оставь источник или проверенные резервные копии и точный статус. Откатывай только собственные изменения, если их текущие digests совпадают с записанными после применения; пользовательские последующие правки требуют решения. Не используй hard reset, force push или массовое удаление каталогов.

## Раздельные коммиты и публикация

Сначала проверь storage mode. При local агентские файлы никогда не stage/commit/push, агентский MR не создаётся. Сам перенос не коммитит и customer cleanup. Позднейший явно запрошенный push продукта выполняется только в customer Git по его policy; ответ: «Агентский Git/MR: не используется — локальное хранение». Не спрашивай remote и не выполняй `git init` для завершения такого push. Следующие правила двух MR относятся только к Git storage.

При настройке сохрани две Git-маршрутизации в artifact documentation/manifest: repository id, роль, проверенные fetch/push URLs, источник правил веток/commit/MR, базовая ветка, обязательные проверки и visibility. Не меняй identity/credentials автоматически и не перенаправляй origin клиентского Git.

- Продуктовые изменения и cleanup ранее отслеживаемых agent artifacts: только customer repository, по его локальным правилам веток, коммитов, MR, reviewers и CI. Не навязывай ему агентские branch/commit conventions.
- Skills/RAG/rules/runtime и отчёт миграции: только artifact repository, по его собственным правилам.
- Используй явные paths при staging, проверь staged diff каждого Git и запрещённые добавления. `commit-plan` — дополнительная проверка, а не разрешение включить чужие изменения.
- Коммиты, push и создание MR выполняй, когда это входит в запрос пользователя. Один только update/перенос не разрешает публикацию. Когда пользователь просит push этой двухрепозиторной работы, процесс включает создание или обновление соответствующих MR/PR и возврат их проверенных URL; merge/auto-merge не подразумевается.
- Если менялись оба репозитория, подготовь два отдельных MR/PR. Customer cleanup — тоже изменение, даже если продуктовый код не менялся. Если один Git не имеет изменений, не создавай пустой MR: явно сообщи «не требуется».
- Повторный запуск использует существующий MR для того же repo/source/target, не создаёт дубликат. Base branch, source branch и URL должны быть проверены, а не угаданы по origin.
- В ответе пользователю выдай две подписанные строки: «Продуктовый MR: …» и «Агентский MR: …». Если публикация одной стороны не удалась, верни успешную ссылку и точный blocker второй; не называй всю публикацию завершённой.
- Не размещай внутреннюю ссылку на агентский MR, RAG, имена приватных skills или подробный внутренний migration report в клиентском MR без разрешения местной политики. Парные ссылки по умолчанию — в ответе пользователю и допустимом внутреннем отчёте. В customer diff может быть виден сам cleanup; отдельно предупреди, если это конфликтует с политикой клиента.

## Приёмка

Подтверждены выбранный storage mode и destination, полнота и сохранность материалов, рабочие ссылки/router, отсутствие новых agent artifacts в customer Git и неизменность продуктового кода/клиентских правил. Для Git проверены visibility и раздельный staged diff; для local — `.gitignore`, publication=never, отсутствие Git у storage и неизменность customer index/HEAD. Отчёт различает файловый перенос, commit, push и MR status; local storage без MR считается нормальным завершением переноса, а не publication blocker.
